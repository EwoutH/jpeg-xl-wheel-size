I tested several ways to reduce this PR's wheel-size impact. **Decoder-only linking removes roughly two-thirds of the JPEG XL download overhead on Linux and macOS. Adding size optimization and LTO removes about 80%.** Windows benefits less, and its size optimizations have a decoding-speed cost in the samples tested.

### Wheel-size impact against `no-jxl`

Each platform's reference is a wheel built from the **same Pillow commit and dependency recipes, with JPEG XL disabled**. The percentages below are growth over that reference, not changes relative to another Pillow release.

![Added wheel download size over no-jxl. On Linux and macOS, growth falls from roughly 25–30% with the PR to 5–6% with decoder-only linking, MinSizeRel and LTO. Windows falls from 8.5% to 6.9%.](https://raw.githubusercontent.com/EwoutH/jpeg-xl-wheel-size/master/figures/jpeg-xl-overhead.png)

| Platform | `no-jxl` wheel | PR: full libjxl | Decoder only | + MinSizeRel | + LTO |
| --- | ---: | ---: | ---: | ---: | ---: |
| Linux x86_64 | 6.971 MiB | +29.8% | +10.1% | +6.6% | +5.5% |
| Linux aarch64 | 6.409 MiB | +24.8% | +8.2% | +5.7% | +4.8% |
| macOS arm64 | 4.565 MiB | +29.1% | +9.4% | +7.0% | +5.9% |
| Windows AMD64 | 6.793 MiB | +8.5% | +8.5% | +6.9% | +6.9% |

For example, on Linux x86_64 the original PR adds approximately **2.081 MiB** to the download; decoder-only + MinSizeRel + LTO adds **0.386 MiB**. On macOS arm64, the corresponding additions are **1.330 MiB → 0.270 MiB**. These are reductions in the *added JPEG XL cost*, not 80% reductions in the whole Pillow wheel.

Uncompressed wheel contents shrink too. On Linux aarch64, JPEG XL adds approximately **4.895 MiB** with the PR settings versus **1.450 MiB** with LTO; on macOS arm64, **3.442 MiB → 0.820 MiB**. This measures unpacked member bytes, excluding generated bytecode and filesystem overhead.

### What looks worth pursuing

1. **Link the existing `jxl_dec` target first.** This gives most of the Unix savings without the size-optimization tradeoff. The patch adds an install rule for that upstream target, links `jxl_dec` and `jxl_threads`, and omits the encoder-only Brotli link on Windows. Box/metadata decoding, animation and JPEG reconstruction remain enabled. The smaller Windows improvement is consistent with its static linking already discarding unused encoder objects.
2. **Evaluate MinSizeRel and LTO separately by platform.** Same-runner sample decoding with macOS arm64 LTO was close to the PR. Windows MinSizeRel/LTO took roughly **1.4–1.5× as long** for the two flower samples, while saving only about 1.4% of the whole wheel. These initial microbenchmarks need broader confirmation before choosing release flags.
3. **Keep SIMD enabled.** Scalar-only compilation saved relatively little beyond LTO, changed some decoded channel values by one level, and substantially slowed decoding. ZIP level-9 recompression also offered little: around **0.1–0.2%** smaller downloads, with no installed-size reduction.

### Validation and remaining work

All six variants have built and passed Pillow's selftest and the selected JPEG XL, JPEG and PNG tests on **Linux x86_64/aarch64, macOS arm64 and Windows AMD64**. Same-runner comparisons of six images found identical sample pixels for decoder-only, MinSizeRel and LTO on macOS arm64 and Windows. Linux aarch64's sample hashes also matched across its independent test jobs. These checks cover a small corpus and one Python ABI, not full codec or release qualification. Intel macOS results remain pending in this snapshot.

The [experiment repository](https://github.com/EwoutH/jpeg-xl-wheel-size) pins this PR to `d00ba3a89faabd31fd92c3b506c86557da8c0a0b`, with CPython 3.13 and libjxl 0.11.2. Reporting reuses Pillow's matching and table rendering from **#9621**; the conclusions above use the same-commit `no-jxl` reference. Dependencies are staged and cached, and saved wheels support test/report retries without recompilation.

Standalone tools/benchmarks are excluded from the optimized builds. They also had to be disabled for the Linux x86_64 PR baseline because a benchmark could not link against the common static libsharpyuv archive; the baseline's codec library and optimization settings remain unchanged. Highway's standalone tests/examples are skipped by the staging harness.

Evidence: [size/test report for the first 23 wheels](https://github.com/EwoutH/jpeg-xl-wheel-size/actions/runs/38309369474), [completed Linux x86_64 PR baseline and tests](https://github.com/EwoutH/jpeg-xl-wheel-size/actions/runs/38309406995), [same-runner macOS comparison](https://github.com/EwoutH/jpeg-xl-wheel-size/actions/runs/38308643532), [same-runner Windows comparison](https://github.com/EwoutH/jpeg-xl-wheel-size/actions/runs/38308639837).
